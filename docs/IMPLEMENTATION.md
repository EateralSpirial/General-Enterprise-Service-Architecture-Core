# Implementation and validation

Current implementation is **0.2.2**, code revision `da179ac3ea1e041775d2f422c90952d58cbbbe48`, on `codex/gesac-runtime`. [Runtime contracts](runtime.md) own the service-host, node, coordination and adapter boundaries. This checkpoint records the implementation and observed deployment; it does not replace the historical CLI prototype evidence.

Implemented capabilities:

- Independent service-host SQLite accounts, scrypt password/passphrase checks, optional TOTP, hashed sessions, plan grants, platform releases, signed artifacts and durable update receipts.
- Multiple independent host/account/trust profiles, plan subscriptions and installed software instances on one node. Native vaults are the default; explicit `sealed` storage supports headless nodes.
- Redis online claims/projections, backed by durable target admission for unresolved operations. Repeated account/device/instance requests retain the original identity; separate devices can update under the same account.
- Ed25519 manifests, bounded paths/files, SHA-256 verification, sequence high-water marks, offline export/import, local adapters and prepare/apply/reconcile/rollback. Offline operation does not require a running service host or Redis.
- Signed self-updates through the independent launcher, retained bootstrap/previous core, and a service-host supervisor that adopts the selected core while retaining the server database.
- Independent node removal, vault/configuration cleanup, and an optional private local lifecycle hook for exact installer-owned services. Failed or uncertain service removal retains node configuration. Managed products and the external service-host business database keep their own ownership.

[CI run 40351936839](https://github.com/EateralSpirial/General-Enterprise-Service-Architecture-Core/actions/runs/40351936839) passed Rust formatting, strict Clippy, tests and release builds on Ubuntu, Windows and macOS, plus Python protocol tests and both real-process E2E suites. The runtime suite covers ten scenarios including multiple hosts/accounts/devices, idempotency, offline operation, Redis/server restart, tampering, uncertain execution, self-update supervision and removal. The legacy suite covers ten signed self-update/recovery scenarios. Ubuntu and the physical Mac each passed 34 Rust tests; their local release builds were also verified.

PAUH integration was deployed on the owner's Ubuntu, AORUSMASTER4090 and MacBook-Air. All three run GESAC **0.2.2** with signed self-update sequence **3**, and Daemon **0.1.23**. GESAC service-host health also reports 0.2.2. Each Daemon has a required configured GESAC instance; startup verifies its managed release before attaching to the native runtime. All three product operations are applied and reported to the service host. Their 164 source and 164 compiled files match byte for byte. Native Core-signed session reads completed on the original three Daemon Manager threads.

PAUH's full release suite passed 623/627 tests with four host-specific skips; affected native suites passed 43/43 on the physical Mac and 29/43 on Windows with fourteen POSIX-specific skips. Disposable real installations on each OS were uninstalled through 0.2.2: the node root and its scoped systemd unit, scheduled task or LaunchAgent disappeared, while an external managed-product sentinel remained. Windows initially rejected installer-created hook files owned by Administrators; assigning the owning current user before retry completed removal. Production hook files have the same private ownership boundary.

Operational receipts belong to PAUH's private `private/deploy/gesac-20261026/`, with build/test logs under `.tmp/gesac-integration-20261026/`. PAUH's `docs/DEPLOYMENT.md` owns exact installations, timers, maintenance identities and recovery. Linux's eight protected unknown records/five files and shared native generation were verified unchanged. The Mac native listener remained identical. A separate Windows background-host maintenance owner replaced its already-exited native generation; the GESAC task retains that owner's receipt rather than claiming an unchanged Windows PID.

Account TOTP is implemented and tested but not enabled on the provisioned unattended account. Multi-host/multi-plan behavior has isolated integration evidence; the deployed fleet currently uses one service host with `pauh` and `gesac` plans. Cross-host high availability, signing-key rotation, server business-database retirement and a graphical account console remain separate capabilities.
